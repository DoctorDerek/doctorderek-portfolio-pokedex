## 1. THE CORE PHILOSOPHIES

You must mathematically optimize your code generation for the following three principles:

- **QREAM (Quality Rules Everything Around Me):** The relentless pursuit of flawless UI/UX, accessibility, and robust functionality. Code that works but feels cheap, fragile, or inaccessible to the end user is a failure of QREAM. Quality is the ultimate arbiter of success.
- **MQA (Minimum QREAM Architecture):** The absolute leanest, most robust architectural foundation required to deliver QREAM. Over-engineering, speculative future-proofing, and complex “spaghetti” logic are explicitly forbidden. Elegant simplicity is mandated.
- **Algorithmic Capital:** The ultimate metric of success. Flawless, bug-free, highly performant code generates user trust and retention (Algorithmic Capital). You are engineering trust, which is the only asset that matters.

## 2. THE 5-STEP FORGE PROTOCOL

You must mentally and explicitly process every task through this sequence to prevent hallucination and over-engineering:

- **Step 0: 0LIST (Audit & Impact).** Audit the codebase for Canonical Ownership (do not duplicate existing logic) and Anti-Monolith rules (do not bloat files). Identify the exact files you will touch.
- **Step 1: 1PLAN (The Blueprint).** Formulate the architectural blueprint based strictly on MQA and all current coding pillars.
- **Step 2: 2CHECK (Red Team).** Verify your 1PLAN against the codebase constraints. Ensure you are answering the exact semantic domain of the issue without scope creep. Check the proposed change against all current coding pillars by canonical number and name. For each, record a finding grounded in this repository or why the pillar does not apply.
- **Step 3: 3CODE (Execution).** Emit the verbatim, unabridged implementation of the plan. No AI slop or unnecessary comments.
- **Step 4: 4CHECK (Verification).** Verify the emitted code compiles without strict TS errors and adheres to MQA. Repeat the full pillar audit against the actual diff and its callers. Run the applicable strict TypeScript and behavior checks.
- **Step 5: 5RUN (QA Checklist).** Emit a concise QA Checklist for Mapachito to manually test the feature/fix locally or via preview deployment.

For an explicitly prose-only change, a brief coding-pillar applicability note is sufficient. UI, styling, configuration, tooling, and test changes use the full audits.

## 3. GIT WORKFLOW & SEMANTIC COMMITS

- **NO PARALLEL WORK:** You will work exactly ONE task, bug, feature, or package group at a time sequentially.
- **The MCP Issue Mandate:** Before writing a single line of code, you MUST use the GitHub MCP server to open an issue for your task. The issue tracks your context and goal; any length or detail is acceptable.
- **Pull Request Linkage:** The PR you open MUST explicitly include the exact string `Closes #<IssueNumber>` in the PR description body to automatically link it to the issue you just created.
- **Small, Atomic, Semantic Commits (CRITICAL):** You must ALWAYS clearly differentiate your work into discrete, small, atomic commits. Never bundle unrelated UI tweaks, TypeScript refactors, and core logic into a single monolithic commit. You must strictly use the format `<type>(<scope>): <subject>` based on these definitions:
  - `feat(scope):` A new feature for the user (not a new feature for a build script).
  - `fix(scope):` A bug fix for the user.
  - `refactor(scope):` Refactoring production code (e.g., improving architecture, removing `any` types, scrubbing comments) with no new features or bug fixes.
  - `chore(scope):` Updating packages, build tasks, or configuration files (no production code change).
  - `style(formatting):` Code formatting (e.g., Prettier fixes, fixing missing semicolons) (no production code change).
  - `docs(scope):` Documentation updates (e.g., updating READMEs).
  - `test(scope):` Adding or refactoring tests (no production code change).
- **The Human-in-the-Loop Handoff:** You are forbidden from pushing, pulling, or merging locally.
  1.  _Your Role:_ Write code locally, make atomic semantic commits, and ALWAYS finish the task by running `pnpm lint` and `pnpm format` (committing any resulting fixes as `refactor(linting): _` and `style(formatting): _`). Then, open the PR via the GitHub MCP.
  2.  _Mapachito’s Role:_ Mapachito handles all `git push` and `git pull` operations via GitHub Desktop, and manually reviews/merges PRs on the GitHub GUI. You must wait for this loop to close before advancing.

Evaluate the complete measurement → state/style update → layout/animation feedback loop for unnecessary rendering, visible corrections, and repeated layout; observation must be justified together with the behavior it drives. Any measurement-based exception requires a concrete approved behavior, demonstrated limitations of declarative layout in supported browsers, and explicit Mapachito approval for the smallest scoped implementation. Cleanup, batching, and passing tests do not establish necessity. Do not introduce a competing styling or measurement framework. You must exclusively use “Curly Double Quotes” (“ ”) and curly apostrophes (’) in all UI-facing text. Straight quotes are banned in the UI presentation layer.

## 5. THE CODING PILLARS OF MQA (MINIMUM QREAM ARCHITECTURE)

You will strictly adhere to all current coding pillars in Mapachito’s Core/Coding Constitution when writing or reviewing any code. The current native Constitution governs their names, definitions, and exceptions. Verify any local mirror against the native source before relying on it.

1. **The Pillar of Good Taste and Quality Over All Other Concerns (QREAM):** Flawless UI/UX, mobile responsiveness, and accessibility are absolute mandates. Before a user commits to a choice, show the facts, available actions and immediate consequences they need. Each control must be discoverable with the input in hand. Give a row or a second view a distinct purpose, such as making a comparison possible. Preserve those decisions and their feedback as available space and input change.
2. **The Pillar of Elegant Simplicity (Anti-Over-Engineering):** Execute the most direct, readable solution; over-engineering and speculative future-proofing are banned.
3. **The Pillar of Empirical Verification (The "No-Assumptions" Law):** Verify all assumptions, API contracts, and package versions with actual terminal data; do not hallucinate. Inspect the canonical documentation, the production implementation and its callers. Verify types, payloads, ownership and readiness through the real path under test. Clarify a consequential ambiguity before acting. Complete every required gate, then direct extra checks toward unresolved risks to correctness, data or usability. Record the revision or deployment, what static inspection established, what ran, what the user accepted and what remains open. After a failure, identify whether the cause is in the product, the diagnostic or the environment. Correct that cause, repeat the affected check and retain the lesson in the existing task record.
4. **The Pillar of ALMOST NO PRINT STATEMENTS (AKA THE PILLAR OF ONLY INSTRUMENT AS A TEMPORARY DEBUGGING TOOL OR AS A PERMANENT QA-ONLY APPROACH IN QA ROOMS):** Console logs are banned in production code; use them only temporarily during active debugging or permanently within isolated QA rooms.
5. **The Pillar of Instantaneous Debugging (We Allow Temporary Print Statements for Debugging Like a Lead SWE, and We Allow Print Statements for QA Rooms):** Use surgical, temporary print statements when actively hunting bugs to trace execution flow immediately. Place probes at the critical points from the initiating action through the consuming handler so the trace shows where the behavior diverges.
6. **The Pillar of Temporary Instrumentation Should Be Deleted:** Scrub all temporary print statements before making any semantic commit to keep the codebase sterile. Retain permanent instrumentation that an isolated QA room requires.
7. **The Pillar of Intellectual Honesty (Anti-Arrogance):** Base architectural confidence on empirical execution success and compiler verification, not unearned assumptions. Identify hypotheses and proposals as such. Earn confidence in the claimed behavior through a successful 5RUN.
8. **The Pillar of No Code Comments Ever:** Code must self-document via strict types and semantic naming. An authored comment is permitted only to prevent a specific regression or explain exceptionally complex logic that the code cannot make clear. Label it “ONE-TIME EXCEPTION” and preserve it during cleanup. Preserve required third-party notices and generator-owned output.
9. **The Pillar of Check the State Directly Not with an Over-Engineered `is_state_active` Custom Function or Hallucination:** Read the active state directly from its React, form, query or state-machine owner. A derived value must express a distinct decision. Avoid boolean wrappers that merely repeat a state check.
10. **The Pillar of No Unnecessary If Statements:** Trust the framework and your strict TS types; fail loudly on bad data rather than writing defensive checks for impossible states. Validate route inputs and external data at the boundary before relying on those types.
11. **The Pillar of No Code Duplication:** Reuse compatible behavior and presentation across features and screen sizes. First inspect the highest existing owner, including whole React components, workflows and design-system patterns. Prefer direct reuse, configuration or composition, a narrow compatible extension, then extraction. When extracting, move every affected consumer onto the same owner. At 0LIST, identify the owning component and its tokens or utilities. At 4CHECK, trace them through the actual caller, including interaction, accessibility, responsive layout, motion and recovery. A new variant or arbitrary value needs a demonstrated gap. Show the closest existing implementation and obtain Mapachito’s explicit approval for any unavoidable duplication.
12. **The Pillar of Unique Access (The "%NodeName Only" Law):** Strictly use absolute path aliases for internal application imports. Relative directory traversal is banned. Use the owning component’s ref when direct DOM access is required.
13. **The Pillar of Trust in the Engine (Anti-Disconnect):** Rely on native React/Next.js memory management; avoid writing unnecessary manual unmounting or teardown boilerplate. An effect must release the subscriptions, listeners or observers it installs outside React’s ownership.
14. **The Pillar of “Don’t You Ever Do ANYTHING ELSE UNNECESSARY”:** Execute exactly the requested scope; do not over-engineer, abstract prematurely, or add unrequested features.
15. **The Pillar of No Vestigial Code (No pass):** Remove empty code blocks, unused imports, unused variables, and abandoned functions immediately. Before removing assets, configuration or generated output, check the real consumers and the reason each item is retained. 16. **The Access .state Directly:** Expose state publicly and access it where needed via hooks or context rather than relying on deep, unnecessary prop-drilling.
